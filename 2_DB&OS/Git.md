# Git. Основы

### Зачем нужен Git?

**Git** — это распределённая система контроля версий. Она нужна, чтобы:
- хранить историю изменений проекта (что, когда и кем было изменено);
- возвращаться к любой предыдущей версии файлов;
- работать над одним проектом нескольким людям одновременно, не мешая друг другу;
- безопасно экспериментировать в отдельных ветках, не ломая основную версию;
- синхронизировать проект между компьютерами и удалёнными сервисами (GitHub, GitFlic и др.).

Проще говоря, Git — это «машина времени» для вашего проекта плюс инструмент командной работы.

#### Почему не флешка?

1. Флешка — потенциальный разносчик вирусов
1. Личные данные с флешки случайно могут попасть на чужой компьютер
1. Антивирус ОС может удалить данные с флешки
1. Флешка может потеряться или сломаться

#### Почему не облако типа Yandex Диск или Google Диск?

1. Облако не контролирует версии данных
1. Своё облако на чужом компьютере — это риск утечки личных данных
1. Для работы с облаком на чужом компьютере необходим браузер, а это не безопасно
1. Нет надёжной фильтрации типов файлов для загрузки и хранения в облаке

#### Преимущества Git

1. Трудно потерять свои проекты
1. Легко отслеживать версии проекта
1. Легко делиться с другими людьми своими проектами
1. Легко разрабатывать проекты совместно с другими людьми (в команде)
1. **Git** по умолчанию интегрирован во многие популярные средства разработки, например **VSCode**
1. В **Git** можно создавать веб-страницы с описанием своих проектов
1. Многие **Git**-сервисы предоставляют возможность автоматизации сборки ваших проектов

#### Основные состояния git-репозитория

1. **Инициализация** — `git init` — превращение обычной папки в репозиторий
2. **Состояние** — `git status` — показать состояние текущего репозитория
3. **Подготовка** (добавлены изменения) — `git add .` — добавление изменений
4. **Фиксация**, сохранение — `git commit -m 'Update README.md - fix'` — сохранение с комментарием
5. **Синхронизация** с удалённым репозиторием — `git push` — сохранение на облачном сервисе, например `Gitflic.ru`

#### Что можно сохранять в git?

1. Обычно небольшие по объёму файлы, < 40 mb.
1. Изображения, документы, mp3, видео
1. Все файлы с именами латинскими буквами без пробелов

### 1. Запуск Git на персональном компьютере

Проверить установку **Git** в **PowerShell**

```shell
git version
```
```shell
git --version
```

Показать справку о Git
```shell
git help
```

**Сменить редактор по умолчанию:**

На редактор кода **VS Code** (элементарный)
```shell
git config --global core.editor "code --wait"
```
На **Micro** (проще для новичков):
```shell
git config --global core.editor "micro"
```
На **Nano** (чуть сложнее для новичков):
```shell
git config --global core.editor "nano"
```

**Представиться системе Git (выполняется однократно, после установки Git или перед 1-м коммитом)**

Команды представления системе **Git**

```shell
git config --global user.name "Your name"
```

> где вместо **Your name** — ваш username

```shell
git config --global user.email "rurewa@mail.ru"
```

> где вместо `rurewa@mail.ru` — ваша почта

> Если вы пользуетесь git на чужом компьютере, то используйте `--local`

### 5. Проверить изменения

```shell
git status
```

Показать состояние удалённого (от слова "далеко") репозитория
```shell
git remote show origin
```
> Команда показывает, какие локальные ветки связаны с удалёнными, и куда будет выполняться `git pull` и `git push`.

Показать сравнение изменения файлов до и после (до `git add`)

```shell
git diff
```
> Сравнивает рабочую директорию с индексом (тем, что уже подготовлено через `git add`). Показывает только ещё не добавленные изменения.

```shell
git diff --staged
```
> Сравнивает индекс с последним коммитом. Показывает то, что уже подготовлено к коммиту. Чтобы выйти из режима просмотра, выполните `Q`.

Отменить изменения в файле (вернуть к последнему коммиту)
```shell
git restore README.md
```

### 6. Подготовить файлы к коммиту (добавить)

> Никогда в разработке не используйте русские имена файлов и каталогов!
> Никогда в разработке не используйте пробелы и спецсимволы в именах файлов и каталогов!

добавить все файлы и папки, включая скрытые
```shell
git add .
```
или все, кроме скрытых
```shell
git add *
```
```.gitignore``` — файл, который содержит **blacklist** несохраняемых файлов.

Отменить добавленные изменения (убрать из индекса, но оставить в файлах)
```shell
git restore --staged README.md
```

### 7. Закоммитить (зафиксировать)

```shell
git commit -m "Some message"
```
или объединить ```git add``` и ```git commit``` для уже отслеживаемых файлов:
```shell
git commit -a -m 'Update README.md'
```
> Текст коммита лучше писать по-английски!

или
```shell
git commit -a
```
> Откроется текстовый редактор командной строки по умолчанию, в котором нужно записать текст коммита

Изменение текста последнего коммита
```shell
git commit --amend
```

### 8. Запушить

```shell
git push
```
> Перед ```git push``` желательно выполнить ```git pull```

или сразу обе команды:
```shell
git pull && git push
```
или более "мягкий" вариант (сначала получить изменения, но не сливать автоматически):
```shell
git fetch && git push
```
> `git fetch` только загружает изменения с удалённого репозитория, но не сливает их с вашей текущей веткой. `git pull` делает и fetch, и merge.

или, если не получилось с 1-го раза запушить, то:
```shell
git push -u origin master
```
`-u` устанавливает связь между локальной и удалённой веткой, чтобы в дальнейшем можно было писать просто `git push`

где **master** — имя нужной ветки. Вместо **master** может быть **main**

### Работа с git-ветками

Показать локальные ветки
```shell
git branch
```
или показать все ветки (в т.ч. удалённые)
```shell
git branch -r
```
или все ветки
```shell
git branch --all
```
Создать новую локальную ветку
```shell
git branch test
```
где `test` — это имя создаваемой ветки

Переключиться на другую ветку
```shell
git switch test
```
> `git switch` — более новый и безопасный способ переключения веток (появился в Git 2.23). В отличие от `git checkout`, он не может случайно «отцепить» HEAD.

или (старый способ)
```shell
git checkout test
```
ещё можно создать новую ветку с автоматическим переходом в неё
```shell
git switch -c test
```
> `-c` (или `--create`) создаёт ветку и сразу переключается на неё. Это транзакционная операция: если переключение не удастся, ветка не будет создана.

Отправить новую ветку на удалённый сервер
```shell
git push --set-upstream origin test
```
где `test` — имя отправляемой ветки

Переключиться на предыдущую ветку
```shell
git switch -
```
или переключиться на указанную ветку
```shell
git switch master
```
Удалить локальную ветку
```shell
git branch -d test
```
> `-d` удаляет только полностью слитую ветку. Если ветка содержит неслитые изменения, Git откажется её удалять. Для принудительного удаления используйте `-D`.

Удалить удалённую ветку
```shell
git push origin --delete test
```

### Слияние веток

Например, ветку **anybranch** слить с **master**

Переходим в ветку master
```shell
git switch master
```
и выполняем слияние 2-х веток в одну
```shell
git merge anybranch
```
> Если слияние происходит без конфликтов и текущая ветка является предком сливаемой, Git выполнит **fast-forward** — просто передвинет указатель вперёд, без создания отдельного коммита слияния.

> Если возникли конфликты, Git остановит слияние. Нужно вручную исправить файлы, затем выполнить `git add .` и `git merge --continue`. Чтобы отменить слияние и вернуться в исходное состояние: `git merge --abort`.

### Файл .gitignore

"Чёрный список" файлов (их расширений), которые не нужно сохранять в проекте. Обычно это временные файлы.

[A collection of .gitignore templates](https://github.com/github/gitignore)

Если папка build уже была добавлена в Git раньше, .gitignore на неё не подействует. Нужно сначала убрать её из индекса:
```shell
git rm -r --cached build/
```
```shell
git commit -m "chore: remove build directory from tracking"
```

### Тэги

Тэги — это постоянные метки, указывающие на конкретные коммиты. В отличие от веток, они не перемещаются. Используются для обозначения релизов и важных вех в истории проекта.

Получить локальные теги:
```shell
git tag
```
Получить удалённые теги (remote)
```shell
git ls-remote --tags origin
```
Удалить локально
```shell
git tag -d v0.0.1
git tag -d v0.1.0
git tag -d v0.1.1
# и т.д. — перечислите все, что не нужны
```
Удалить на GitHub
```shell
git push --delete origin v0.0.1
git push --delete origin v0.1.0
git push --delete origin v0.1.1
```
> Удаление локального и удалённого тега — две разные операции. Удаление на GitHub не удаляет тег локально, и наоборот.

Создать тег, например для нового релиза

Подготовим изменения
```shell
git add .
```
Добавим коммит
```shell
git commit -m "feat: adaptive theme support"
```
Запушить
```shell
git push
```
Создать **аннотированный** тег (рекомендуется для релизов — содержит автора, дату и сообщение)
```shell
git tag -a v0.1.0 -m "Release v0.1.0: adaptive theme support"
```
> Аннотированные теги (`-a`) предпочтительнее для релизов, так как хранят метаданные. Легковесный тег (`git tag v0.1.0`) — это просто указатель на коммит без дополнительной информации.

Запушить тег на сервер
```shell
git push origin v0.1.0
```
